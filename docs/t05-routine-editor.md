## 화면과 이동

1. 하단 **루틴** 탭 → **루틴 관리**로 목록에 진입한다.
2. **루틴 등록**으로 새 편집 화면을 열거나 목록의 루틴을 눌러 수정한다.
3. 루틴명과 단계 이름·예상 시간(분)을 입력한다. **단계 추가**, 각 단계의 위·아래·삭제 버튼으로 구성을 바꾼다.
4. **루틴 저장** 성공 후 목록으로 돌아가 저장소를 다시 조회한다.
5. 목록의 삭제 아이콘은 확인창을 연다. 취소하면 원본을 유지하며 확인한 경우에만 삭제한다.

목록에는 단계 수와 전체 예상 시간을 표시한다. 편집 중에는 유효한 단계의 합계를 즉시 갱신하고 미입력 단계가 있으면 합계에서 제외됐음을 표시한다. 조회 실패를 빈 목록으로 취급하지 않으며 재시도를 제공한다.

## 입력·ID·편집 정책

- 공백뿐인 루틴명·단계명, 빈 단계 목록, 미입력·비숫자·0·음수·1440분 초과 예상 시간을 거부한다.
- 새 시간 입력은 정수 분 단위(1~1440분)다. 전체 합계는 정확히 24시간까지 허용한다. 최소 1분은 UI 정밀도 선택이며 모델의 양수 Duration 제약과 구분한다.
- 기존 저장값에 분 미만 정밀도가 있으면 정확한 값을 설명에 표시한다. 시간을 수정하지 않은 단계는 원래 Duration을 보존한다. 사용자가 시간을 수정한 경우에만 새 정수 분 값으로 적용한다.
- 루틴 ID와 단계 ID는 이름·목록 인덱스 대신 보안 난수 128비트의 32자리 16진 문자열로 한 번 생성한다. 새 루틴은 조회한 루틴 ID와, 새 단계는 현재·제거된 초안 단계 ID와 충돌하는지 검사한다.
- 기존 ID는 이름·소요시간 수정과 단계 순서 변경으로 바뀌지 않는다. 동명 단계도 서로 다른 ID를 가진다. 순서는 `Routine.steps`의 목록 순서로 저장한다.
- 원본 모델은 수정하지 않고 별도 컨트롤러 초안을 편집한다. 저장 시에만 새 `Routine`·`RoutineStep`을 생성한다.
- 저장 실패 후 같은 초안과 ID를 유지한다. 오류를 표시하고 **다시 저장**을 제공한다.
- 변경이 있는 상태에서 뒤로가기·편집 취소를 누르면 **계속 수정 / 저장하지 않고 나가기**를 확인한다. 미변경 화면은 바로 나간다. 앱 프로세스 종료에 대한 미저장 초안 자동 복구는 제공하지 않는다.
- 저장·삭제 처리 중 중복 요청 및 이탈을 막는다. 목록에서 주입받은 저장소는 닫지 않으며 화면이 생성한 저장소만 종료한다.

## 계층·범위

화면은 `RoutineStore`를 주입받는다. 기본 SQLite 저장소 생성 함수는 앱 조립 계층에서 전달하며 화면은 SQL을 직접 실행하지 않는다. 목록에서 연 저장소는 편집 화면과 공유한다.

실행 기록 저장·수정·삭제 API를 호출하지 않는다. 기존 SQLite 저장소는 루틴 정의와 실행 스냅샷을 별도 테이블에 보존한다. 복수 루틴 중 계획에 사용할 루틴 선택(T07), 시간 계산(T06), 실행(T09), 실행 복구(T14)는 추가하지 않는다. 설정·저장 스키마를 확장하지 않았다.

## 검증 구분

최초 구현 시 정적 분석·전체 테스트 73건·Android 빌드가 통과했다. 이후 T04·T05 규약 점검으로 전체 테스트를 171건으로 확대했다. 최신 결함 수정과 Android 관측은 [UI 점검 보고서](t04-t05-ui-audit.md)를 따른다.

`app/test/routine_screen_test.dart`에 대역 저장소 기반 화면 검증과 실제 SQLite 기반 통합 검증을 분리했다.

| 구분 | 검증 내용 |
|---|---|
| 대역 저장소 UI | 신규 등록, 동명 단계, 순서·ID 유지, 편집 취소, 삭제 취소, 빈 목록, 조회·저장·삭제 실패와 재시도, 중복 요청 차단 |
| 입력 검증 | 공백 이름, 예상 시간 누락·0·음수·비숫자·상한 초과, 전체 합계 상한, 정확히 24시간, 마지막 단계 삭제, 기존 분 미만 시간 보존 |
| 레이아웃 | 320×640, 큰 글자 2배, 키보드에 해당하는 하단 inset에서 편집·순서 변경·저장 |
| 실제 SQLite | 빈 DB에서 UI 등록, 이름·순서 수정, ID·소요시간 재조회, DB·화면 재생성 복원, UI 삭제 후 DB 재개방, 과거 실행 스냅샷 보존 |

위젯 테스트의 SQLite 파일 재개방은 실제 Android 프로세스 재시작 검증과 구분한다. 추가 점검에서 닫힌 SQLite의 조회·저장·삭제 오류와 손상 payload를 UI에 전달하는 실제 저장소 시험도 수행했다. 물리적 저장 장치 장애 전체를 재현한 것은 아니다.

검증 명령:

```powershell
cd app
flutter analyze
flutter test --no-test-assets
flutter build apk --debug
```

`--no-test-assets`는 생성된 테스트 자산이 있을 때 사용할 수 있다. 최초 실행은 기본 `flutter test`로 셰이더를 포함한 자산을 생성한다.

Android 최초 빌드는 기존 `app/build/app/intermediates/assets/debug/mergeDebugAssets`를 삭제하지 못해 실패했다. 해당 폴더 보존 후에도 기존 `native_assets/jniLibs` 삭제 오류가 발생해 `app/build` 전체를 `app/.dart_tool/t05-build-backup-*`로 이동·보존했다. 새 출력 폴더에서 재빌드한 결과 `app/build/app/outputs/flutter-apk/app-debug.apk` 생성에 성공했다. 소스·DB·SDK 버전은 이 조치로 변경하지 않았다.
