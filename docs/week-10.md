## 디버깅 요청 4요소 / Four parts of a debugging request

- 증상 Symptom: 알람 설정을 바꾸거나 다시 울림을 요청할 때 새 예약이 실패하면 기존 알람까지 사라질 수 있다.
- 재현 Steps: 미래 시각 A를 예약 → 시각 B로 변경 → 주입한 플랫폼에서 B 예약 실패 또는 부분 적용 뒤 오류 → OS 예약과 내부 캐시·오류 결과 확인.
- 기대 Expected: 새 예약 성공 전에 이전 예약·울림을 제거하지 않으며, 실패·복원 결과를 호출자가 확인할 수 있어야 한다.
- 실제 Actual: 수정 전 기존 예약 소실·부분 적용 2건을 재현했다. 수정 후 PR #32 집중 11건과 PR #33 Kotlin JVM 10건을 통과했다. 권한 철회·만료·복원 실패까지 예약 보존을 보장하지는 않는다.

## 데모 시나리오 초안 / Draft demo scenario

아래는 기존 Must와 [T12 시나리오](test-scenarios.md)에 따른 **UI 연결 후 수행할 초안**이다. 아직 전체 제품 흐름의 수행 결과는 아니다.

1. 테스트 기기·OS·빌드 커밋·권한·음량을 기록하고, 목표 도착·이동·수면 시간과 짧은 루틴을 저장한다. 재조회 후 권장/수동 기상·실제 알람·취침·출발을 구분한다.
2. 가까운 미래의 알람을 설정해 소리·진동·해제·다시 울림을 확인한다. 알람 해제가 기상 확정이 되지 않는지 본다.
3. 감지 구간 안에서 실제 화면 켜짐으로 후보와 확인 요청을 확인한다. 확인 전 조건부 예상 도착·지각을 표시하고, 취소·중복 신호·수동 보완도 확인한다. 테스트 이벤트를 사용하면 화면과 발표에서 구분한다.
4. 기상을 확정하고 루틴을 시작한다. 단계 완료·건너뛰기·예상시간 초과 시 도착·지각 갱신을 확인한다. 수동 루틴 시작만으로 기상을 확정하지 않는다.
5. 실행 도중 앱 프로세스를 다시 시작해 후보·실행 상태와 경과 시간을 확인한다. 종료 후 저장 기록을 확인한다. 기록 조회 화면 T16 완성과 저장 검증은 구분한다.
6. 권한 거부·예약 변경 실패의 오류 안내와 재시도 경로를 확인한다. 날짜를 바꾼 다음 회차는 명시적으로 계획하며 매일 자동 반복으로 설명하지 않는다.

제품 적용 전 TC05 재감지 기본 1분과 TC10A 알림 권한 거부 시 새 예약 차단 기준을 맞춘다. 후속 #24 로컬 문서에 정리돼 있으나 main의 T12 문서 반영과 실제 T13 수행은 남아 있다. 자동 감지의 지원 상태가 불충분하면 팀에서 대체 방식·범위를 결정해야 하며, 수동 시연으로 자동 감지 검증을 대체하지 않는다.

### 2026-11-07 #23 요구 적합성 회귀 수정
