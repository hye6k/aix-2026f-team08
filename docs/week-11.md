## 데모 시나리오 / Demo scenario — 사용자 한 명의 이야기

아침 등교를 준비하는 사용자가 기본 루틴을 등록하고 준비에 필요한 시간을 입력한다. 앱은 입력된 값을 바탕으로 아침 계획에 필요한 시각을 계산해 보여준다. 교수님께 기본적인 루틴 등록과 계산 기능을 중심으로 현재 구현 상태를 설명했다.

## 시연 결과 / 실패 지점 / Result and failure point

- 기본 루틴 등록과 이를 바탕으로 한 간단한 계산 기능을 보여드렸다.
- 데모 빌드를 시연 직전에 준비해 충분히 사전 시연해 보지는 못했다. 따라서 이번에 보여준 범위와 전체 기능의 안정성 검증을 구분한다.
- 당시 팀은 주요 기능 구현이 상당 부분 진행됐으며 이후 UI를 개선하고 세부 기능을 보완할 계획이라고 설명했다. 이는 당시 진행 상황에 대한 설명이며 제품 전체의 통합·실기기 검증 완료를 뜻하지 않는다.
- 제품의 Android 실기기 알람·감지와 앱 상태별 동작 검증은 [#17](https://github.com/hye6k/aix-2026f-team08/issues/17)에서 별도로 추적한다.

수업 현장에서 교수님이나 다른 팀으로부터 별도의 피드백을 받지는 않았다. 아래는 개발 과정의 GitHub 리뷰·대응 기록이며, 수업 이후 반영된 내용도 포함한다.

- #12 / PR #31 리뷰에서 활성 단계 최소 잔여 시간의 적용 경계, 루틴 완료 후 출발 가정, 시계 역행 검사 범위를 확인했다. 기존 계산 동작을 명시하고 각 경계에 대한 자동 검사를 보완했다. 실제 출발·도착 감지와 마지막 계산 이후의 시계 변경 감지는 이 계산 범위에 포함하지 않는다.
- #23에서 계획·기상·루틴·알람의 세션 계약을 선행 기능이 병합된 main에 분리하고, 저장 실패와 예약 재시도·중복 조작·복원 경계를 자동 검사했다. SQLite와 Android 기동 연결은 #24에서 검증한다.
- #24에서 기존 DB의 세션 저장·기동 및 복원 코드를 분리하고 기존 화면과 저장소 소유권 경계를 검토했다. 활성 계획 편집을 세션에 연결하는 화면과 제품 실기기 검증은 후속으로 남긴다.
- PR #36 리뷰에서 대기 의도 없는 알람 재적용 실패의 복원 누락과 초기화 중 종료 시 구독 잔류를 재현하고, 저장 순서와 구독 정리를 수정해 회귀 검사했다.
- PR #37 리뷰를 반영해 알람 오류의 사용자 확인 전 보존, 알람 대기 시각의 현지 시간 표시 규칙, Android 앱 상태별 지원 범위와 후속 통합·검증 순서를 보완했다. 제품 실기기 결과는 별도 확인한다.
- #24 후속으로 기존 설정·루틴 화면의 편집을 활성 세션과 연결해 계획·알람 재계산 및 저장 후 OS 적용 대기 안내를 검증한다. 계획 해제·대기 재시도 UI는 별도로 남긴다.
- 계획·기상·루틴·기록 화면을 세션에 연결하고 날짜별 단발 계획, 권한·알람 재시도, 조건부 예상과 진행 상태를 표시한다. 주입한 기상 신호를 실제 Android 감지와 구분한다.
- PR #38 리뷰에서 설정 저장 성공 메시지가 알람 적용 실패 안내를 지우는 문제를 실제 SQLite와 설정 화면으로 재현했다. 설정·루틴 저장 완료 후 저장과 알람 대기를 함께 안내하도록 고치고 각각 화면 검사를 추가했다.
- PR #39 리뷰에서 다른 날짜의 수동 기상 입력으로 현재 계획의 알람이 취소될 수 있는 경계를 확인했다. 계획의 권장 기상일을 표시하고 세션에서도 날짜를 검증하며 자정을 넘는 계획과 거부 시 저장·취소 불변을 검사했다. 진행 중 계획 변경 안내, 작업 실패와 알람 대기 안내의 구분, 기기 오류 확인 후 상태 재조회도 보완했다. 실기기 동작은 #17에서 별도로 확인한다.


## 성찰 / Reflection — 가장 약한 고리

중간 데모는 기본적인 루틴 등록과 계산을 보여줬지만, 빌드를 시연 직전에 준비해 실제 사용자 흐름을 충분히 반복 확인하지 못했다. 기능 단위 구현과 자동 검사만으로 전체 화면 연결이나 실기기 동작을 완료했다고 판단하기 어렵다는 점이 가장 약한 고리였다.

이후에는 UI와 핵심 흐름을 연결한 뒤 사용자 조작 경로를 미리 검토하고, Android 실기기에서 알람·감지·권한과 앱 상태별 동작을 확인해야 한다. 리뷰 중 발견한 문제는 재현과 수정 후 다시 검증하고, 미검증 범위는 완료 결과와 구분해 기록한다.
